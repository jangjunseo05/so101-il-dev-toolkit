# 중앙 서버 웹서비스 전환, 왜 지금은 안 하는가 (그리고 나중에 하려면 어떻게)

"서버 하나만 띄우고, 도메인 주소로 접속하면 로컬에 아무것도 설치하지 않고도
MuJoCo 렌더링이나 텔레옵을 웹에서 바로 쓸 수 있게" — 네이버나 유튜브 같은
평범한 웹서비스를 쓸 때처럼 만들 수 있는지 검토한 결과를 정리한다.

**결론부터**: 지금 파이프라인의 절반(①데이터 수집, ④추론 중 실시간 관찰)은
이런 방식으로 못 만든다. 코드를 잘 짜고 못 짜고의 문제가 아니라 **물리적으로
불가능**하기 때문이다. 나머지 절반(②QA 검증, ③학습)은 사실 지금도 중앙화가
가능하고, 필요해지면 의미도 있다.

## 1. 한눈에 보기

| 단계 | 뭘 하는 단계인가 | 로컬에 물리 하드웨어가 꼭 필요한가 | 중앙 서버로 옮길 수 있나 |
|---|---|---|---|
| ① 데이터 수집 | 실물 리더암을 손으로 움직여 로봇 동작 녹화 | ✅ 필요 (USB로 연결된 로봇팔) | ❌ **불가능** |
| ② QA 검증 | 녹화된 데이터 통계/이상치 분석 | ❌ 없음 (순수 계산) | ✅ 가능 |
| ③ 학습 | GPU로 정책(ACT) 학습 | ❌ 없음 (GPU만 있으면 됨) | ✅ 가능, 오히려 유리 |
| ④ 추론 | 학습된 정책으로 MuJoCo에서 자율 동작 관찰 | 트랙에 따라 다름(아래 참고) | 🟡 부분 가능 |

- ④는 두 가지 모드가 있다: **트랙 A**(헤드리스로 몇 초 돌려보고 에러만
  확인)는 실시간으로 볼 필요가 없어서 중앙화 가능. **트랙 B**(MuJoCo 창을
  띄워 직접 눈으로 관찰)는 ①과 똑같은 실시간 문제를 그대로 안고 있어서 불가능.

## 2. 왜 ①(과 ④의 트랙B)은 안 되는가

### 비유로 먼저

네이버에 접속할 때, 네이버 서버가 내 책상 위에 꽂힌 USB 기기를 직접
조종해야 하는 일은 없다. 그냥 내 요청을 받아서 결과 화면만 돌려주면 끝이다.

그런데 이 프로젝트의 ①은 다르다. **내 책상 위에 실제로 놓인 로봇팔(리더암)을
손으로 움직이면, 그 움직임이 실시간으로 시뮬레이션 로봇에 그대로 반영돼야
하는 작업**이다. "웹사이트에 접속해서 내용을 본다"가 아니라 "웹사이트가
내 방에 있는 하드웨어를 실시간으로 조종한다"에 가깝다. 이 차이 때문에
일반적인 웹서비스 상식이 그대로 적용되지 않는다.

### 막히는 지점 ①: 하드웨어는 물리적으로 한 곳에만 있다

로봇팔은 특정 컴퓨터의 특정 USB 포트에 꽂혀 있다. "서버 하나 + 아무 데서나
접속" 모델에서는 그 서버가 내 USB 포트에 직접 손을 뻗을 방법이 없다.
가능한 방법은 딱 두 가지뿐인데, 둘 다 막힌다.

| 방법 | 설명 | 왜 안 되는가 |
|---|---|---|
| (a) 로컬 브릿지 프로그램 | 내 컴퓨터에서 작은 프로그램을 하나 계속 띄워두고, 그게 USB 신호를 읽어 서버로 보낸다 | "로컬에 아무것도 안 깔아도 된다"는 목표 자체가 깨진다. 지금(Streamlit 전체를 로컬 실행)보다 설치할 게 줄어들지도 않는다 |
| (b) 브라우저가 USB에 직접 접근 (Web Serial API) | 브라우저 자체 기능으로 USB 포트를 읽는다 | 크롬/엣지 계열에서만 되고 사파리·파이어폭스는 안 됨. 무엇보다 지금 검증된 파이썬 로봇 제어 코드(`lerobot` 라이브러리)를 자바스크립트로 처음부터 다시 만들어야 함 — 비용이 매우 큼 |

즉 어느 쪽을 택해도 "그 하드웨어와 물리적으로 같은 자리에 있는 무언가"가
필요하다는 사실 자체는 사라지지 않는다.

### 막히는 지점 ②: 실시간 제어에는 네트워크 지연이 치명적이다

설령 위 문제를 어떻게든 풀었다고 치자. 이제 로봇의 물리 연산(MuJoCo)을
중앙 서버에서 돌리면 다음과 같은 경로가 생긴다.

```
내 리더암을 움직임 → [인터넷] → 서버가 물리 계산 → 화면 그림 →
[인터넷] → 내 브라우저에 표시
```

이 프로젝트는 초당 50번(20밀리초에 한 번씩) 로봇 자세를 갱신하면서, 사람이
**화면을 보면서 그리퍼로 물체를 정밀하게 집는** 작업을 한다. 화면이 조금만
늦게 반응해도 "지금 집었나?"를 헷갈리게 된다.

이번에 브라우저 스트리밍 기능을 로컬에서 붙여봤을 때 실측한 결과, **같은
컴퓨터 안에서 화면을 그리는 데만도 정해진 시간 예산의 최대 38.5%**를 썼다.
여기에 인터넷 왕복 지연(같은 건물 와이파이면 몇 밀리초지만, 일반적인
인터넷 환경에서는 수십~수백 밀리초)까지 얹으면 체감 렉이 상당해진다.

그리고 이 프로젝트는 "잘 수집된 시연 데이터"가 전체 파이프라인의 근본
재료다 — 렉이 있는 상태로 녹화한 동작은 그 자체로 품질이 의심스러운
학습 데이터가 되어버린다.

### 그럼 클라이언트에서 물리 연산을 돌리면 되지 않나? (WebAssembly)

이것도 검토했었다(이전 아키텍처 검토 참고). 결론은: 이 방법을 쓰면 위
"막히는 지점 ①"(하드웨어 브릿지 문제)이 그대로 남아있는 데다가, 이번엔
**학습에 쓰는 이미지와 화면에 보이는 이미지가 서로 다른 렌더러(파이썬 vs
브라우저)에서 나오게 되어 둘이 미묘하게 달라지는 문제**까지 새로 생긴다.
즉 "중앙 서버에 물리 연산을 두는 방식"과 "브라우저에 물리 연산을 두는
방식(WASM)"은 서로 다른 방향이지만 결국 같은 벽(하드웨어는 로컬에 있다)
앞에서 막힌다.

## 3. 뭐는 되는가 — ③학습은 오히려 중앙화가 자연스럽다

②QA 검증과 ③학습은 로봇 하드웨어와 아무 상관이 없다. ②는 순수 계산(통계
분석)이고, ③은 GPU 연산이다. GPU는 원래도 "여러 사람이 나눠 쓰는 공용
자원"이라는 개념이 자연스러운 물건이라, 학습 단계만 따로 떼서 공용 서버로
옮기는 건 기술적으로 충분히 말이 된다.

지금은 팀원 각자 자기 컴퓨터의 GPU로 학습하는 구조다. 만약 "여러 팀원이
각자 모은 데이터를 한곳에 모아서 더 큰 모델을 같이 학습하고 싶다"는 필요가
실제로 생긴다면, 그때는 학습 서버 중앙화가 투자할 가치가 있는 선택이 된다.

## 4. 나중에 진짜로 전환을 고려한다면

### 언제 고려해야 하나 (트리거 조건)

아래 같은 구체적인 필요가 생겼을 때만 시작하는 걸 권한다 — "그냥 최신
기술을 써보고 싶다"는 이유로는 들이는 노력 대비 얻는 게 적다.

- [ ] 여러 팀원의 데이터를 한곳에 모아 하나의 더 큰 모델을 학습하고 싶다
- [ ] 개인 GPU로는 감당이 안 되는 규모의 학습이 필요해졌다
- [ ] 학습 결과를 팀 전체가 실시간으로 같이 보고 싶다 (지금도 각자 화면에서 가능하지만, 한곳에 모아 비교하고 싶은 경우)

### 범위 — 한 번에 다 바꾸려 하지 말 것

**① 데이터 수집, ② QA, ④ 추론(트랙 B)은 그대로 로컬에 둔다.** ③학습(과
학습에 쓸 데이터 업로드 경로)만 떼어서 중앙화하는 하이브리드 구조로
시작하는 걸 권한다. 전체를 한 번에 웹서비스로 바꾸려는 시도는 위 2절의
벽에 부딪혀 실패할 가능성이 높다.

### 새로 필요해지는 것들 (체크리스트)

지금 코드는 "믿을 수 있는 한 사람이 자기 컴퓨터에서만 쓴다"는 전제로
만들어져 있다. 여러 사람이 하나의 서버를 같이 쓰는 순간 아래가 전부
새로 필요해진다 — 하나라도 빠지면 위험하다.

- [ ] **데이터 업로드 경로**: 로컬에서 녹화한 데이터를 서버로 보내는 방법.
      (다행히 이 부분은 이미 절반쯤 준비돼 있다 — 이 프로젝트가 쓰는
      데이터셋 형식은 허깅페이스 표준 형식과 호환되어, `push_to_hub`라는
      업로드 기능이 이미 그대로 동작하는 걸 확인해둔 상태다.)
- [ ] **사용자 구분(로그인/권한)**: 지금 코드에는 "누가 지금 이 서버를
      쓰고 있는지" 구분하는 개념이 전혀 없다(로그인 기능 0건). 이 상태로
      여러 명이 동시에 학습 버튼을 누르면 서로 충돌한다.
- [ ] **보안**: 지금 구조는 웹 버튼을 누르면 서버가 그대로 프로그램을
      실행하는 방식이다. "믿을 수 있는 나 혼자 쓰는 컴퓨터"에서는 안전하지만,
      인터넷에 열어두는 순간 낯선 사람이 서버에서 임의 명령을 실행할 수
      있는 위험한 구조가 된다. 반드시 별도 보안 설계가 필요하다.
- [ ] **GPU 줄서기(스케줄링)**: 여러 명이 동시에 학습을 걸면 순서대로
      기다리게 하는 큐가 필요하다. 지금은 GPU가 사용 중이면 그냥 거부만
      하는 수준이다.
- [ ] **서버를 어디에 둘 것인가**: 회사/학교 서버든 클라우드든, 이건
      코드 문제가 아니라 예산과 운영 담당을 정하는 문제다.

### 권장 진행 순서

1. ③학습만 떼어서 별도 프로젝트로 설계 시작 (①②④는 손대지 않음)
2. **로그인/사용자 구분부터 설계** — 나중에 끼워 넣으려면 훨씬 어려워지므로 가장 먼저
3. 데이터 업로드 경로 만들기
4. GPU 줄서기(스케줄링) 붙이기
5. 마지막으로 필요하면 웹 화면(대시보드) 정리

## 5. 이 판단을 다시 검토해도 되는 경우

아래 조건이 바뀌면 ①에 대한 판단도 다시 볼 여지가 있다 — "영원히 절대
불가능"은 아니다.

- 초저지연(수십 밀리초 이하) 네트워크 인프라가 갖춰지는 경우
- 데이터 수집을 실물 로봇 없이 순수 시뮬레이션만으로 하기로 방향이
  바뀌는 경우 (그러면 애초에 "물리적으로 로컬에 있어야 하는 하드웨어"
  자체가 사라짐)
